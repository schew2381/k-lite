k-lite

You write YAML saying what should run. A control plane that survives losing a member makes the nodes agree, gives every service a name, and lets you say who may talk to whom.

Four Go binaries plus two borrowed engines, all on plain Docker: klited (stateless brains over an etcd trio) · klite-agent (one per node) · klite-net + Envoy (each node's switchboard) · klite (the CLI). This page is the whiteboard the project started on — cleaned up, animated, and kept honest about what got erased along the way.

1 · Declare

klite apply hands any server replica a wish list — workloads, services, nodes, policies. It all lands in etcd, and nothing imperative ever leaves your terminal.

2 · Converge

Every agent watches for its share of the wish list and nudges Docker until reality matches. Kill a container and it comes back, restart count showing.

3 · Discover

Instances call each other by name. DNS answers with a stable per-node VIP, and the Envoy behind it checks policy, then relays to a healthy replica.

4 · Survive

Containers crash, nodes drain, and even the lead server can die mid-rollout. The lease moves, another replica's controllers wake up, and traffic never notices.

04 · how it got here

The same board, erased and redrawn three times

The design ran as an interview in rounds: numbered questions, a recommendation for each, the plan recomputed after every answer. Facts went to agents, and every decision stayed with us. Of round 1's five recommendations, two survived contact. Every post-it below is a real decision record (ADRs 0001–0017 in docs/adr/, narrative in docs/design-log.md), reversals included. Those make the best slides.

highlight = new that round dashes = erased that round

Round zero is a photo, not a design. The brief asked for everything declared in YAML, driven through some server with a CLI, run on nodes, and discoverable by name — on local Docker now, real cloud nodes someday. The margins already held the stretch goals: internet-joined nodes with auth, a UI, live mutation, and network policies. One drawing on that board survives verbatim into the product, an arrow between two services with a red ✕ through it.

The draft plan optimized for smallness: one server owning a bbolt file, agents asking for work over HTTP long-poll, and a per-node container running hand-rolled DNS plus a small TCP proxy. Policies were ordered firewall rules. A planning agent stress-tested the macOS data path and verified the two Docker facts the whole design rests on, namely that embedded DNS forwards unknown names to a per-container upstream and that static IPs outside the dynamic range are safe to hand-manage.

Four choices from this round never moved again:

  1. agents dial out
  2. the switchboard lives in a container, because macOS gives no choice
  3. every Service gets a VIP per node
  4. the agent, not Docker, restarts whatever crashes

Round 1 put five questions on the table, each with a recommendation, and two survived. The argument that carried discovery: adopting a proxy never buys you out of the resolution layer, because something of ours must still say what the name b means. So nginx, caddy, and traefik only outsource byte-forwarding, and the meshes that solve both halves require Kubernetes underneath.

Round 2 followed the answers to their conclusion. If the point is demonstrating real cluster behavior, the control plane should survive losing a member and the data plane shouldn't be a homemade proxy destined for the bin:

  • bbolt got erased for a three-member etcd with stateless klited replicas in front
  • Envoy took the proxy job, making klited a miniature istiod speaking real xDS (spike-gated, with the fallback written down)
  • policies switched to Istio's DENY-then-ALLOW model
  • "delete the old instance" grew into drain choreography, with a DRAINING state that stops new connections before old ones die

grill round 2ADR 0007

istio-lite policies

DENY always wins. A Service no ALLOW targets accepts everyone, and the first ALLOW flips it to allowlist mode. No priority integers to shadow each other.overround 1's ordered rules, k8s's famously misread semantics

grill round 2ADR 0009

Drain before death

Cordon → surge replacements → Ready → DRAINING → SIGTERM → SIGKILL. A rolling update is the same dance, one instance at a time.claimzero failed requests during rollouts and node drains — the verify scripts assert it

grill round 2ADR 0010

The scheduler stays modest

Filter (pin, Ready, not cordoned, under maxInstances), then pick the emptiest node. resources: becomes cgroup limits, never placement.so thatevery scheduling decision has a one-line explanation a demo can say out loud

grill round 2ADR 0012

Round 3 hardened the edges and wrote the rules for writing things down. A join token now buys a real certificate: the agent sends a CSR, klited's own CA signs it, and every stream after that is mutually authenticated. A remote node needs a server address, a token, and an outbound connection, nothing more. The UI gained a policy simulator, because the evaluator is a pure function and exposing it costs one endpoint. And we made the recording discipline binding — every decision gets its ADR the moment it's made, vocabulary changes update CONTEXT.md in the same commit, and each design session appends to the log this very section is drawn from.

Tokens buy certificates

One-time join token → CSR → per-node mTLS client cert from klited's CA. Agents and each node's Envoy authenticate every connection with it. Rotation is out of scope, and says so.overbearer tokens forever, one shared cluster secret

grill round 3ADR 0013

A policy simulator in the UI

"Can a reach c?" runs the same pure evaluator the RBAC filters and the PolicyCheck RPC use — one function serving three surfaces.plustopology with red deny edges, live tables, log tails, YAML apply. The facade's endpoint list is frozen here.
