k-lite

a small Kubernetes built from scratch, to find out why the real one is shaped the way it is

Declarative YAML goes in, scheduled containers come out, and service discovery, mTLS, and network policies run on top of plain Docker. All of it runs today — the same cluster the k-lite web UI shows live. This page walks the whole design in fourteen lessons, each one standing on the last, with the wire truth (addresses, ports, RPC names) kept exact.

1 · Declare

klite apply hands any server replica a wish list — workloads, services, nodes, policies. It all lands in etcd, and nothing imperative ever leaves your terminal.

2 · Converge

Leader-elected controllers compare the wish list to reality and write what's missing. Each node's agent watches for its share and nudges Docker until they match.

3 · Discover

Instances call each other by name. DNS answers with a stable per-node VIP, and the Envoy behind it checks policy, then relays to a Ready instance — even one on a machine across the internet.

4 · Survive

Containers crash, nodes drain, and the lead server can die mid-rollout. The lease moves, another replica's controllers wake up, and traffic never notices.

every box on this board gets its own lesson — blue is the control plane talking, green is real traffic, red is policy saying no

02vocabulary

Six nouns carry the whole design

k-lite deliberately renames the Kubernetes ideas it rebuilds — reaching for the k8s word means importing the k8s assumptions, and half this project is noticing where those assumptions come from. Each card ends with the closest Kubernetes cousin, struck through the way it's struck from the codebase (CONTEXT.md bans them in identifiers and output).

Workload

A named set of identical Instances run from one container image, plus how many to run. spec.replicas is the only imperative-looking number in the system, and it's still a wish.

k8s: Deployment

Instance

One running copy of a Workload, scheduled to a Node and backed by exactly one container. Named b-7da4: workload dash random suffix.

k8s: Pod, replica

Service

A stable name and port that routes to the Ready Instances selected by a label. b:8080 is what callers type, whatever churns behind it.

k8s: Service (same word, same idea)

VIP

The virtual IP a Service resolves to on a given Node. Each Node's proxy owns its own VIP per Service, fixed for the Service's lifetime.

k8s: ClusterIP — but per (Service, Node)

Node

A machine that runs Instances. Locally it's one agent process pretending to be a machine, and later it's real hardware running the same binary.

k8s: Node (kubelet's machine)

Endpoint

One Instance viewed as a routing target, carrying a readiness state — READY takes traffic, DRAINING finishes what it has.

k8s: EndpointSlice entry

four more nouns arrive with the lessons that need them:

Ingress port

The host port through which other machines reach one Endpoint on this Node over mTLS. Allocated per Endpoint from the Node's fixed slice.

k8s: NodePort — but per endpoint, and TLS-required

Advertise address

The machine address a Node announces for its ingress ports. Every other machine must be able to reach it — lesson 11 is about what happens when one can't.

k8s: node ExternalIP, roughly

NetworkPolicy

Named ALLOW or DENY rules between Services. DENY always wins, and a Service that no ALLOW targets accepts everyone.

k8s: NetworkPolicy in name, Istio AuthorizationPolicy in spirit

Infra pod

Two per-Node system containers sharing one network namespace: name resolution and traffic routing for that Node's Instances. The k8s word is borrowed on purpose — this pair is exactly what Kubernetes calls a pod.

k8s: pause container + friends (lesson 5 builds one)

the renames are the point: when this page says "Instance", you know every fact about it came from this design, not from k8s folklore

03state & watches

Everything is an object in etcd, and everyone watches

Those nouns need somewhere to live. Every one of them is a small YAML-shaped object stored in etcd under one key scheme, and every moving part of k-lite (controllers, agents, the UI) is a loop that watches those keys and reacts. Learn this one pattern and lessons 4 through 11 are variations on it.

klited itself keeps nothing. Any replica can take your klite apply, validate it, and write it to etcd with a compare-and-swap on the object's revision. Reads and watches also go straight to etcd from any replica. The only thing one replica has that the others don't is a 5-second lease under /klite/leader: whoever holds it runs the controllers (lesson 4), and when it dies, another replica's controllers wake up against the same state.

Two facts about the watch carry the whole system. Every write bumps a global revision, so "what changed since revision 1213" is a real question etcd can answer. And a watcher gets the event, not a diff — the whole new object, or the whole old one on delete. That's why every consumer can be a dumb loop: list everything once, then apply events forever.

One wrinkle you'll meet again in lesson 4: some kinds are server-materialized. You can klite get vipallocations, but apply rejects them — a leader controller writes them, and your YAML has no business there. They exist so allocator decisions (which VIP, which ingress port) are durable, watchable state instead of something recomputed differently by every replica.

the keyspace, as the UI's etcd browser shows it

# one prefix per kind, one key per object /klite/v1/workloads/b spec.replicas: 2 /klite/v1/instances/b-7da4 spec.node: node-1 /klite/v1/services/b port 8080 → 80 /klite/v1/nodes/node-1 status.phase: READY /klite/v1/networkpolicies/… # server-materialized — apply rejects these /klite/v1/vipallocations/b.node-1 10.44.64.4 /klite/v1/ingressallocations/b.b-7da4 port 20002 # not an object: the controllers' lease /klite/leader ★ one klited holds it

why etcd and not a file? the grill's answer: the moment klited is stateless, you get HA, watches, and CAS for free — and killing the leader mid-rollout becomes a demo, not an outage. ADR 0005 has the full argument.

Before moving on: who is allowed to write /klite/v1/instances/…?

check your answer

Not you. Instances are server-materialized. The workload controller creates them, the scheduler fills in spec.node, and the owning agent reports their status. Your apply only ever touches the Workload, and the rest is derived. That split is the next lesson.

04declare → converge

One apply, and the cluster catches up

So a wish lands in etcd. Nothing has run it yet — turning it into containers is a relay of watch-loops, each owning one small step. Walk the relay once with the player, then break it on purpose: kill an instance, kill the lead server, or replay the whole relay.

1

The five controllers, and what each one owns

"The controllers" above is really five leader-only loops, each watching a few kinds and converging one relationship. None of them talk to each other — they only read and write objects, and the objects are the coordination.

  • workload compares each Workload's replicas to its living Instances, creates the missing ones (unscheduled), deletes the surplus, and steers rollouts when the template changes.
  • scheduler finds Instances with no spec.node and picks one: honor a pin, drop nodes that are NotReady, cordoned, or full, then take the emptiest. Ties break by name, so placement is explainable in one sentence (ADR 0012).
  • node watches heartbeats. 15 quiet seconds turns a Node NotReady, and 30 more evacuates it: its Instances get deleted so the workload controller replaces them elsewhere.
  • vip materializes one VIPAllocation per (Service, Node) from the 10.44.64.0/18 pool (lesson 5), and releases them when either side goes away.
  • ingress the same shape for cross-machine ports: one IngressAllocation per (Service, Instance), drawn from the owning node's 32-port slice (lesson 11).

Beside them, every replica runs the endpoints engine — the non-controller that recomputes "which Ready instances back which service, reachable how" on every event, and feeds both Envoy (lesson 8) and the agents. It can run everywhere because it writes nothing: it derives.

And draining?

The same machinery runs node maintenance. klite drain node-2 cordons the node, and the workload controller does the rest: surge a replacement elsewhere, wait for it to turn Ready, retire one old instance to DRAINING, let it finish for up to 30 seconds, delete it, repeat. One retirement stays in flight at a time, so capacity never dips. Rollouts ride the identical sequence when a template changes, tracked by the hash stamped on each Instance. The one recorded exception: when no node has room to surge, a drain-first fallback retires before replacing, and ADR 0010 keeps that trade-off written down.

05a node, up close

What "node-1" physically is

The relay ends with "the agent runs a container" — time to meet the machinery that makes that container's world work. A local node is not a VM and not a container-in-a-container. It's one host process plus a labeling convention, and everything interesting lives in two containers it builds first.

Locally, a node is one klite-agent process on your Mac. That process is the node's whole identity. It registered as node-1, it heartbeats for node-1, and it runs node-1's share of the containers under node-1's certificate. Five nodes means five agent processes, and "adding a node" is starting one (lesson 10 makes that a button).

The containers themselves — from every node — run flat on the single shared Docker daemon, side by side on one bridge network called klite0. There is no nesting and no per-node network boundary. Docker-in-Docker would have given a real boundary, and ADR 0003 rejected it: privileged containers, slow startup, and nested networking that misbehaves on macOS.

What keeps five agents out of each other's containers is label discipline. Every container carries io.klite.node=<name>, and an agent's entire worldview is the Docker API filtered to its own label. Agent 1 never touches agent 2's containers even though they sit on the same daemon. Names encode it too: klite.node-1.b-7da4 is instance b-7da4 on node-1.

A "real" node later is the same picture minus the simulation: the same agent binary on its own Linux machine with its own Docker daemon. The flat-shared-bridge shortcut disappears and the ingress-port path (lesson 11) carries cross-node traffic instead. That's the payoff of one-agent-per-node over one-agent-simulating-N. The Runtime Docker wrapper, the dial-out agent protocol, and the label discipline are identical either way, so cloud nodes are a swap, not a rewrite.

node-1, as the Docker daemon sees it

$ docker ps --filter label=io.klite.node=node-1 klite.node-1.net klite-net:dev 10.44.0.11 klite.node-1.envoy envoy:v1.31.5 (joins .net's netns) klite.node-1.b-7da4 busybox:1.36 10.44.128.6 klite.node-1.a-963d busybox:1.36 10.44.128.2 # same daemon, different node — not node-1's problem: klite.node-2.b-265f busybox:1.36 10.44.128.9

the infra pod is a hand-built pod. klite-net starts first and owns a network namespace. Envoy starts with --network container:klite.node-1.net and joins it, so two containers share one netns and one IP — which is exactly what Kubernetes calls a pod. We needed one, so we built one (ADR 0008).

The two containers that make a node a node

  • klite-net (the donor) answers DNS on :53 for the svc.klite zone (the UI badges this job kdns, and these lessons borrow the name). It also holds the node's VIPs as /32 addresses via netlink and TCP-probes the node's instances every 2 seconds with a 1-second timeout. Verdicts report through the agent, because on macOS the host can't reach container IPs at all — the data path had to live in a container (ADR 0008).
  • Envoy joins that namespace so it can bind listeners on the very VIPs klite-net holds — freebind lets it bind them even before they exist on the interface. It's a stock upstream image, and everything it knows arrives over xDS (lesson 8).
  • Docker rejects most options on a container that joins another's netns, so everything namespace-scoped rides the donor: the static IP, NET_ADMIN, the published ingress-port slice, and the host.docker.internal mapping.
  • Every instance container is started with --dns 10.44.0.11 --dns-search svc.klite --dns-opt ndots:1 — one resolver, the node's own. The ndots:1 is load-bearing: without it, musl-based images skip the search domain and bare names like b die (a spike caught this live).

Docker just assigned a brand-new container 10.44.64.9. What went wrong?

check your answer

Everything — that address sits in the VIP pool, and Docker never allocates from it. The bridge is created with ip-range 10.44.128.0/17, so Docker's own IPAM can't reach 10.44.64.x, and an agent that finds a klite0 with different IPAM refuses to adopt it. An address like that means the network wasn't created by k-lite at all.

and the doors inside the node? klite-net's admin port (:9090) and Envoy's admin port (:9901) sat open on the bridge until ADR 0029 — any tenant container could have rewritten a node's DNS. The fix wasn't auth: a one-shot helper container joins the infra pod's netns and drops those ports for VIP and instance source ranges with iptables. Workloads lose the ports, the host keeps its debugging window.

06an instance is born

Scale b to 3, and follow the new instance in

Lessons 4 and 5 gave you the relay and the machinery. Now run the same scale-up under a microscope, keeping your eye on one instance the whole way — loop by loop, address by address.

1

What "Ready" costs, and what dying costs

The phases you just watched are written by two different hands. The agent reports Pending → Running from Docker's mouth, and Ready arrives only when klite-net's 2-second TCP probe connects to the instance's readinessProbe.tcpPort. Readiness is judged from inside the network, by the thing that will route to it — not by the control plane hoping.

Death runs the same loops backwards. Containers run with --restart=no, because Docker restarting things behind the agent's back would mean two owners for one truth (ADR 0011). The agent sees the death event, reports Failed, waits a backoff, and starts a fresh container — the same Instance object with its restart counter bumped, so the record keeps the history. Only if the node dies does the instance move: the node controller evacuates after 45 quiet seconds, and the workload controller births a replacement wherever the scheduler points next.

the phase ladder, and who writes each rung

Pending workload ctrl made it; scheduler adds node Running agent: docker start ok, IP known Ready agent, once the TCP probe connects DRAINING workload ctrl: retiring, no new calls Failed agent: crashed — backoff, restart ↻+1

no readinessProbe in the spec? then Running is enough and the agent reports Ready immediately — the probe ladder is opt-in

07a calls b

What actually happens when a calls b

b serves traffic on three instances now, so let's send it a call. Inside a's container something runs wget http://b:8080. That bare little URL sets off the whole discovery design, from a search domain to a proxy with opinions. Step through it, then flip the deny switch and watch where the same call dies.

1

Three choices hiding in that walkthrough

  • The answer depends on who asks. kdns tells node-1's instances node-1's VIP for b, and node-2's instances node-2's. Every caller talks to its own node's proxy — kube-proxy's semantics, arrived at independently (ADR 0006). One cluster-wide VIP was rejected because all local nodes share one bridge, and two proxies claiming one IP is an ARP fight.
  • Records live 5 seconds, and existence is public. A denied caller still gets the A record — the connection is what dies, so a policy denial (connection reset) never looks like a typo (NXDOMAIN). "a knows b exists" was a stated requirement, and ADR 0017 pinned it.
  • Staleness is absorbed, not fought. The VIP is fixed for the Service's lifetime, so a resolver that ignores the 5s TTL (JVMs love to) keeps a correct answer. Churn happens behind the VIP, in EDS — which is the next lesson.

can a caller just skip its proxy? Locally, yes: on the shared bridge any container can dial 10.44.128.6:80 directly, and ADR 0009 accepts that bypass. Policy is a chokepoint on the sanctioned path — the only path DNS ever reveals — not a firewall around the instance. Across machines the front door is stronger: lesson 11's ingress listeners demand a cluster certificate that workloads don't hold.

A teammate says "DNS load-balances across b's instances." What actually balances?

check your answer

Not DNS — kdns always answers with one fixed VIP. The balancing is Envoy's: the VIP listener's cluster round-robins over the Ready endpoints EDS gave it. DNS picks a proxy, and the proxy picks an instance, per connection.

08how Envoy knows

Three xDS APIs, one ADS stream

That proxy just made three decisions: which listener owns the VIP, whether the caller may pass, and which instance gets the connection. It made them from configuration nobody wrote by hand. Envoy learns everything over xDS, the same discovery protocol Istio speaks, served by klited itself.

xDS is a family of "discovery services", one per resource type. The classic quartet is LDS (listeners), RDS (HTTP routes), CDS (clusters), and EDS (endpoints). k-lite serves three of the four. RDS never appears, because every listener here is a plain L4 tcp_proxy — no HTTP routing means no routes to discover. What a service means is already decided by the time the connection reaches Envoy: the VIP names the service, so only "where" remains.

  • LDS delivers the listeners: one per Service, bound to that node's VIP with freebind (lesson 5), carrying the RBAC filters and a tcp_proxy. Plus, after lesson 11, one mTLS ingress listener per local endpoint.
  • CDS delivers one cluster per Service — type EDS, round-robin — and a static one-endpoint cluster behind each ingress listener.
  • EDS delivers the endpoints per cluster with health attached: READY endpoints take traffic, DRAINING ones finish what they hold. Local endpoints are raw instanceIP:targetPort, remote ones are machineAddress:ingressPort.

The L4-only choice has a price worth naming: no HTTP routes also means no HTTP-level policy, so a deny is per-connection, never per-request. Certificates skip xDS too — there's no SDS. They're files the agent mounts into Envoy, fingerprinted into its config hash, so a changed certificate recreates the proxy rather than hoping it re-reads disk.

All three ride one ADS stream — a single gRPC connection from each Envoy to klited, multiplexing the three types in a server-controlled order. That ordering is the point of ADS: a cluster must exist before endpoints reference it, and one stream makes the sequencing enforceable instead of hopeful.

a 30-line bootstrap, then everything else is discovered

# ~/.klite/agent/node-1/envoy-bootstrap.yaml (agent-written) node: { id: node-1, cluster: klite } dynamic_resources: ads_config: # ONE stream for all types api_type: GRPC grpc_services: [{ envoy_grpc: { cluster_name: xds } }] cds_config: { ads: {} } lds_config: { ads: {} } static_resources: clusters: # the only static thing: klited itself - name: xds # host.docker.internal:7443, mTLS, # the node cert from lesson 9

who computes it? every klited replica runs the endpoints engine and an xDS server — whichever replica an Envoy dials must be able to answer. The engine re-derives each node's snapshot on every watch event, and the snapshot version is just the engine's revision counter. New version, one push, hitless swap.

09identity

A token, a CSR, and one dual-purpose certificate

Everything so far ran on one machine, where "who's calling" barely matters. The moment a second machine appears, every connection in the cluster needs an identity on each end. k-lite's answer is a private CA inside klited and a k3s-shaped bootstrap: a shared token buys each node exactly one certificate, and the certificate does everything after that.

klited mints its own CA at first boot (ECDSA P-256, ten years) and stores it under ~/.klite/server/tls. From then on, klite node token prints a join token with a deliberate shape:

K10<sha256 of ca.crt>::node:<cluster secret> └ pins WHO the server must be └ proves WHO you are

The pin solves the bootstrap paradox: the joining agent doesn't have the CA yet, so it can't verify the server's TLS — but it can check that the certificate it's shown hashes to the pin in the token. A wrong secret and a tampered pin both die without persisting anything. The secret is the cluster token klited was started with, so minting the "same" token twice returns the same string — revoking it means rotating the cluster secret, not crossing out one copy.

With the pinned connection up, the agent generates a P-256 key locally, sends a CSR, and gets back a certificate. The private key never crosses the wire. The server discards every name in the CSR and stamps its own: CN=klite:node:node-4. And since ADR 0036, the certificate carries both TLS purposes — ClientAuth for dialing klited, ServerAuth so the node's Envoy can be a server on its mTLS ingress listeners: one identity, both directions.

what the certificate does not say: it names a node, never a service. Any workload on a certified node can be dialed by any other node's proxy, and the dialing side verifies the chain, not that the cert belongs to the specific node EDS named. ADR 0034 and 0036 record both gaps, and per-service identity (the SPIFFE-shaped upgrade) is named future work rather than an accident.

10a node joins

From "declared" to Ready, on any machine

Identity in hand, joining is almost an anticlimax — which is the design working. Membership is declared first: klite apply a Node object, and a card appears on the board, NotReady, waiting for its machine. An agent for an undeclared name is refused. Then somewhere, an agent starts.

On this machine

# the UI's join dialog does this for you (one button — # the facade starts the agent itself, ADR 0040) klite-agent --node node-4 --token K10…

Locally that's the whole ceremony, because the defaults already point at 127.0.0.1:7443. The new process registers, receives its NetBootstrap (its infra IP 10.44.0.14, the VIP pool, its ingress-port slice, the cluster id), builds its infra pod, and starts heartbeating. Fifteen seconds of silence would mark it NotReady; instead the card flips Ready and the scheduler starts counting it.

Over the internet

# on the new machine — needs curl and root # (klite node add prints this exact line for you) curl -sfL https://github.com/…/releases/latest/download/join.sh | \ KLITE_URL=203.0.113.7:7443 KLITE_TOKEN='K10…' KLITE_NODE=node-5 sh -

A real machine shouldn't need a Go toolchain. A tag push publishes release binaries for three platforms plus join.sh, and the infra-pod image goes to a public registry (ADR 0038). The script fetches the right klite-agent, leaves a systemd unit restarting it forever, and from there the flow is byte-for-byte the local one: same Register RPC, same CSR, same NetBootstrap. The bootstrap also pins the infra-pod image cluster-wide, so every node runs the same donor.

One prerequisite sits on the cluster side: the local playground boots klited on loopback, so an off-machine join needs it listening on 0.0.0.0:7443. That costs one flag and no certificate work — the serving certificate re-mints at every boot and bakes each interface address into its SANs, so the machine's LAN IP is already valid for TLS.

why the swap is boring, by construction

  • Agents dial out, always (ADR 0004). Control traffic is agent→klited gRPC streams, so a machine behind NAT joins fine — nothing ever dials into a node for control. Log streaming rides streams the agent opened.
  • The Runtime interface is the only Docker. The agent drives containers through one Go interface, and nothing in it assumes the daemon is shared. On a real machine it simply gets its own.
  • Label discipline doesn't care whose daemon it is. io.klite.node=node-5 filters a private daemon exactly as well as a shared one.
  • The bridge is created on demand. First agent on a machine creates klite0 with the same subnet plan, and later agents validate-or-fail against it.

the one thing that changes: on a shared daemon, node-1 could reach node-2's instances directly over the bridge. On real machines that shortcut is physically gone — and lesson 11 is about the path that replaces it, because the local cluster now uses that path too.

The join, step by step

1

Why does k-lite refuse to register an agent whose Node object doesn't exist yet?

check your answer

Membership is declared, not discovered (ADR 0018). If holding a token were enough to add capacity, the cluster's shape would be whatever showed up. Declaring first keeps the wish list authoritative — a stolen token can impersonate a declared, absent node at worst, not invent new ones.

11across the internet

The same call, when b lives on another machine

a on node-1 calls b, and this time the pick lands on an instance living on node-5, across the internet. The first five steps are lesson 7 verbatim — that's the design holding still. Then EDS answers with something new, and three extra hops carry the connection over the wire, encrypted, without the control plane ever touching a byte.

1

The bookkeeping that made those hops possible

  • Ingress ports are allocations, not guesses (ADR 0035). One stored IngressAllocation per (Service, Instance), from the owning node's slice. An instance selected by N services burns N of the node's 32 slots — accepted at demo scale, and recorded as the first knob to revisit.
  • Listeners follow allocations, not health. Deriving them from endpoint health would reintroduce LDS/EDS skew during churn, with the listener vanishing while connections still drain. Allocation-driven listeners predate traffic and outlive Ready.
  • Identity is reused wholesale (ADR 0034, 0036). Both proxies authenticate with the node certificates the join flow already issued — the trust-delta postit from lesson 9 applies on this wire.
  • The source side still decides everything. EDS names the exact endpoint, so balancing and draining stay in the calling proxy. The ingress listener is a dumb, authenticated funnel to one instance.

Who must reach whom

Reachability is two separate questions, because the two kinds of traffic point different ways.

Mixed clusters, and the asymmetry worth knowing

Can local Mac nodes and real internet nodes share a cluster? On the control plane, completely — every node is the same dial-out agent, and klited can't tell them apart. The data plane is where symmetry ends, because ingress requires that other machines can dial your advertised address, and the two kinds of node advertise very different things.

A workload on node-3 wants to skip policy and dial b-9c2e through node-5's ingress port directly. What stops it?

check your answer

The handshake. The ingress listener requires a certificate chained to the cluster CA, and workloads never hold one — the node identity lives with the infra pod. So lesson 7's local bypass doesn't cross machines. Note what the listener does not check: per-service policy. Identity is node-level (ADR 0034), and policy enforcement stays at the caller's proxy.

A local node's default advertise address, host.docker.internal, only means something to containers on your own Mac. Local→local works, local→remote works (your Envoy dials their public IP), but remote→local dies: the internet node can't resolve the name, and your Mac is behind home NAT anyway. Worse than an error, it's a quiet failure — joining never proved anyone could dial in, so the NATed node registers, heartbeats, and looks healthy while traffic aimed at it dies. A real Linux box carries its own version of the trap: the agent's address self-detection can land on the Docker bridge (172.17.0.1), which only that machine can reach — the reason join.sh refuses to guess when it finds only private addresses, and the reason --advertise-address is effectively mandatory on real nodes.

Within one network, the whole asymmetry dissolves with the same flag. Give every node an --advertise-address the others can dial (for local nodes, the Mac's own LAN IP — the donors already publish their port slices on 0.0.0.0, so LAN IP + ingress port reaches a local instance through Docker's port mapping exactly as it would on a real node), and traffic flows both directions. For the true open internet, ADR 0034 accepts the constraint and writes it down: keep callable services on reachable nodes. The recorded escape hatch is a WireGuard mesh (research/overlay-wan.md's option B), which buys encryption and NAT traversal at the price of key lifecycles, MTU care, and a rendezvous story.

12the live UI

How the board hears about everything

Every lesson so far ends with objects changing in etcd — and the web UI you've been picturing is just one more watcher at the end of that chain. The same watch that drives the controllers drives the pixels, translated twice on the way to your browser, and nothing in the chain polls.

Browsers don't speak gRPC, so a small hand-written facade (klite-facade) sits beside klited and translates: REST for lists and actions, Server-Sent Events for the watch, chunked text for log tails. It holds no state and no store connection — it's a ClusterService client with the admin token, exactly like the CLI (the gate table in lesson 9 already covered it).

The stream itself delivers changes only, with no replay and no resume. So the browser bootstraps the only safe way: list everything, then watch, folding each event into an immutable snapshot that React re-renders. If the stream drops, the store resets and bootstraps again — honest about the gap instead of pretending continuity. Deletes carry the object's last body (etcd's PrevKV), which is how a card can animate out with its name still on it.

Two details make the board feel alive rather than merely correct. The seeded apps are chatty — every instance serves its hostname and rolls a 2.5% chance each second to call a random peer through the full data path, so today's eight seeded instances hum at about a dozen real calls a minute (ADR 0039 records the choice, halved since to keep the board readable). And the UI ships a complete in-browser simulator behind the same client interface: mock mode runs the whole cluster story with no backend at all, which is how the frontend was built and demoed before klited could serve it (ADR 0023).

one change, end to end

# you click ＋ on workload b POST /api/workloads/b/scale {"replicas":3} → ClusterService.Scale (CAS on replicas) → etcd: /klite/v1/workloads/b rev 1214 # …lessons 3–5 happen: create, schedule, start, probe… etcd watch → Watch RPC → facade SSE: event: ADDED data: {instance b-3f81, Pending} event: MODIFIED data: {instance b-3f81, Running} event: MODIFIED data: {instance b-3f81, Ready} # the store folds each event; React draws the chip

One thing this pipeline doesn't carry: the calls themselves. Objects change rarely and traffic flows constantly, so calls ride a second feed. The facade polls each node's Envoy counters once a second and streams the deltas over SSE — ADR 0024's promised route, served at last by ADR 0041. A delta names the caller's node, the target service, and the exact dial target, which is everything the board needs to fly a dot per real call.

seen in the wild: a scale-up on this Mac goes ADDED→Ready in about 180 ms — so fast the UI adds a one-second display dwell per phase, purely so humans can watch Pending become Running become Ready.

15the decisions

Sixteen ADRs, with the roads not taken

These are the sixteen records that carry the architecture, each with what was chosen, what was rejected, and what the choice still costs. The full log — forty records and counting — lives in docs/adr/. The repo's rule is that a decision gets its ADR the moment it's made, and code that contradicts an ADR is wrong until a superseding one lands. Click any card for the full story.

ADR 0003 · lesson 5

A local node is an agent process, not a VM

Five nodes on one Mac = five host processes sharing one Docker daemon, kept apart by labels.

what was rejected, and the price ▾

rejected

  • Docker-in-Docker per node. Truer isolation, but privileged containers, slow startup, and nested networking that misbehaves on macOS.
  • One agent simulating N nodes. The least code, and a fiction for the scheduler and drain logic to exercise.

consequences

  • Label discipline is load-bearing: docker ps --filter label=io.klite.node=x is a node's entire worldview.
  • All local instances share one bridge — the flat shortcut ADR 0034 later had to kill.
  • Adding or removing a node is starting or killing a process.
ADR 0004 · lessons 10–11

gRPC everywhere, and agents always dial out

Typed streams with mTLS in the transport, and a NAT-friendly direction baked in from day one.

what was rejected, and the price ▾

rejected

  • HTTP long-poll + SSE + callback POSTs. Curl-debuggable, but hand-rolled framing when xDS is gRPC anyway.
  • WebSockets (k3s remotedialer style). One connection, but we'd be designing a framing protocol gRPC already is.
  • grpc-gateway for the browser — codegen to serve five routes, when the hand-written facade is smaller.

consequences

  • The server can never call an agent — logs and any future exec ride streams the agent opened.
  • A proto toolchain enters the build, and the facade can drift from the protos (it did — ADR 0026).
ADR 0006 · lesson 7

Our own DNS, and a VIP per (Service, Node)

Names resolve per node to a fixed VIP where balancing, readiness, and policy get to stand.

what was rejected, and the price ▾

rejected

  • Docker network aliases. Zero infra, but nothing gates on readiness and policy has no chokepoint.
  • Env-var injection. Stale on every reschedule, plus start-order dependencies.
  • DNS straight to instance IPs. Client resolver caches (JVMs: 30s) keep serving the dead.
  • One cluster-wide VIP. The k8s shape, but two proxies claiming one IP on a shared bridge is an ARP fight.

consequences

  • Stale client DNS caches stay correct — churn is absorbed behind the fixed VIP.
  • IPAM grows a control-plane pool (10.44.64.0/18), and answers legitimately differ per asking node.
ADR 0007 · lesson 8

Envoy is the data plane, speaking real xDS

Build a miniature istiod rather than a homemade proxy — and gate the bet on a spike.

what was rejected, and the price ▾

rejected

  • A custom Go L4 proxy. A few hundred lines we'd own, meaning a few hundred lines of connection-handling bugs. Kept as the spike-gated fallback.
  • Traefik / Caddy. Dynamic routing but awkward exactly where we need per-VIP listeners at runtime.
  • nginx — reload-based config, wrong for per-second churn.
  • Consul / Istio / Linkerd. Each imports a system larger than k-lite itself.

consequences

  • The spike passed (CDS/EDS/LDS over one ADS stream on colima/arm64, hitless RBAC deny under load), so the fallback stays unused.
  • Debugging moved to config_dump and admin stats — industrial behavior for readable code, eyes open.
ADR 0008 · lesson 5

Everything instances must reach runs in the infra pod

macOS can't route to container IPs, so the data path lives in containers — two of them, sharing a netns.

what was rejected, and the price ▾

rejected

  • Host-side data path. Impossible on macOS, and it would quietly re-couple the design to "control plane shares a machine with instances."
  • One combined image. Fewer parts, but we'd maintain a fork of Envoy's image and marry its upgrade cycle.

consequences

  • Startup sequencing matters: klite-net owns the netns, Envoy joins it, and everything netns-scoped rides the donor.
  • ndots:1 keeps bare names alive on musl images: Docker writes ndots:0 when DNS is overridden, and the search domain dies with it.
  • Needing to reinvent the pod is the best available argument for why Kubernetes has them.
ADR 0012 · lesson 4

Scheduling spreads by count, resources are limits

Filter, then take the emptiest node. Declared cpus/memory become cgroup limits, never placement input.

what was rejected, and the price ▾

rejected

  • Resource-aware bin-packing. The real k8s scheduler's job, invisible on one Mac where every "node" shares the same cores.
  • Ignoring resources entirely. Simpler, but then YAML can't express limits Docker readily enforces.

consequences

  • Every placement has a one-line explanation, which a demo needs more than optimality.
  • If genuinely heterogeneous nodes ever join, this is the ADR to supersede.
ADR 0013 · lesson 9

Nodes join with a token, then hold an mTLS certificate

Token bootstrap into a CA-signed identity, k3s-shaped. Every stream after that is mutually authenticated.

what was rejected, and the price ▾

rejected

  • Bearer node tokens forever. A secret string is all an attacker needs, and revocation is a config edit someone forgets.
  • One shared cluster secret. Demo-grade, no per-node identity at all.

consequences

  • klited carries CA code, and the WAN posture falls out free: a remote node needs an address, a token, and an outbound connection.
  • Certificate rotation is out of scope for v1 — written down so the omission can't be mistaken for an accident.
  • Outcome: ADR 0028's gate classifies callers by these certs, and 0034/0036 reuse them for the data plane, as predicted.
ADR 0017 · lesson 7

Names live under svc.klite, answer in 5s, never deny existing

What a types is b:8080. The search domain makes it b.svc.klite, and kdns answers even callers a policy denies.

what was rejected, and the price ▾

rejected

  • NXDOMAIN for denied callers. Leaks less topology, but a policy denial becomes indistinguishable from a typo.
  • Long TTLs. Pointless when the VIP behind the name never moves.

consequences

  • A denied call fails fast with a connection reset, cleanly different from "no such service" — debugging stays sane.
  • The 5s TTL bounds staleness for resolvers that respect it, and the fixed VIP covers the ones that don't.
ADR 0022 · lessons 3–4

VIP allocations are a first-class stored kind

One VIPAllocation per (Service, Node), reconciled by a leader controller — durable, watchable, debuggable.

what was rejected, and the price ▾

rejected

  • Hash-derived VIPs. No storage, but collisions need probing anyway, and then the mapping isn't derivable without replaying it.
  • A map inside Service status. Fate-shares user spec with server-owned allocations, and every node join churns a CAS on every Service.

consequences

  • Apply rejects the kind — server-materialized, like Instance.
  • Leaked VIPs become a visible bug (klite get vipallocations), not silent exhaustion.
ADR 0026 · lesson 12

The frontend adopts the facade's real dialect

The UI guessed a wire contract before the facade existed. When they met, the UI moved.

what was rejected, and the price ▾

rejected

  • Change the facade to match the UI's guess. Rewriting someone's in-flight work to satisfy a guess inverts the burden, and the facade's choices were the defensible ones.
  • Two type layers, one per dialect. Every consumer would need to know where an object came from.

consequences

  • One decoder at the seam normalizes both dialects, and everything past it sees canonical shapes.
  • The watch has no resume, so reconnect = reset + fresh list — recorded as a known gap, honestly.
ADR 0029 · lesson 5

Admin ports get iptables, not authentication

klite-net's and Envoy's admin ports were open to every tenant on the bridge — one helper container closes them.

what was rejected, and the price ▾

rejected

  • mTLS on the admin APIs — Envoy's admin endpoint can't demand client certs, so half the problem survives.
  • Stop publishing Envoy admin. Closes the host's main debugging window and does nothing about bridge-side access.

consequences

  • A run-once alpine helper joins the donor netns and drops :9090/:9901 for VIP and instance source ranges, so workloads lose the ports while the host keeps its debugging window.
  • The rules apply idempotently and survive agent restarts.
ADR 0034 · lesson 11

Cross-machine traffic rides published ports behind proxy mTLS

Remote endpoints render as machineAddress:ingressPort, and both proxies authenticate with node certs. Ends 0016's deferral.

what was rejected, and the price ▾

rejected

  • Published ports, plaintext. The smallest change, with every cross-node byte readable and nothing checking who dialed.
  • WireGuard mesh. Stays the recorded second step, for when NAT traversal or flat instance IPs matter.
  • Relay through klited. Rejected outright: the control plane must never sit in the data path.

consequences

  • The flat-bridge shortcut is gone everywhere — locally the advertise default is host.docker.internal, so the TLS handshake runs in every demo, not only in production.
  • Mutual reachability is required, and a NAT'd node fails quietly — the asymmetry lesson 11 teaches.
  • Identity stays node-level: any workload on a certified node is dialable by any other node's proxy. The per-service upgrade is named future work.
ADR 0035 · lesson 11

Ingress ports are allocations, and listeners follow them

One stored IngressAllocation per (Service, Instance), fixed at birth. Listener lists derive from allocations, never health.

what was rejected, and the price ▾

rejected

  • Ports in InstanceStatus. Fate-shares a server-owned allocation with agent-written status, the shape 0022 already rejected.
  • Listeners derived from endpoint health. Reintroduces LDS/EDS skew during churn: the listener vanishes while connections still drain.

consequences

  • A remote endpoint without its allocation is omitted from EDS entirely — the flat-bridge path is dead, not a fallback.
  • Ports burn per (service, instance): an instance selected by N services takes N of its node's 32 slots. Accepted at demo scale, first knob to revisit.
ADR 0036 · lesson 9

Node certificates carry both TLS purposes

ClientAuth-only certs broke the moment an Envoy presented one as a server — BoringSSL: "unsuitable certificate purpose."

what was rejected, and the price ▾

rejected

  • A separate serving cert delivered in the Register response. Zero CA changes, but the private key would cross the wire, defeating the CSR flow's whole point.

consequences

  • One line in the signer: ClientAuth + ServerAuth, the same dual-purpose shape Istio issues.
  • Pre-M9 identities self-heal by silently re-joining when a token is in hand.
  • Recorded trust delta: the dialing side verifies the chain, not that the cert belongs to the specific node EDS named — tightening to SAN matching is the known next step.
ADR 0038 · lesson 10

Real machines join from GitHub Releases

A tag push builds three platforms of binaries plus join.sh, and NetBootstrap pins the infra image cluster-wide.

what was rejected, and the price ▾

rejected

  • Clone and go build on each node. Every node carries a Go toolchain plus repo credentials, and re-joining stops being one line.
  • Ship the agent as a container. Manages the host from inside a container, and still needs a public registry.
  • Ansible and friends. The right shape at fleet scale, three files of ceremony for one box.

consequences

  • A node needs curl and root. Release binaries build with CGO_ENABLED=0, so a future cgo dependency breaks the cross-build loudly.
  • The image pin rides NetBootstrap because image skew across nodes is exactly the drift it exists to prevent.
ADR 0039 · lesson 12

Demo apps chatter, and verify gates run their own probers

Seeded services roll a small per-second chance (2.5% today) to call a random peer — ambience for the board, useless as evidence.

what was rejected, and the price ▾

rejected

  • Frozen YAMLs for verify, chatty only in demos. The premise failed: the verify scripts consume the same seeded apps.
  • Random chatter as the test denominator. A 5% roll means windows pass or fail on luck.

consequences

  • Zero-failure gates moved to deterministic probers the scripts own, riding the same kdns → VIP → Envoy → ingress path.
  • Landing the shared script surfaced two real bugs: a shell-join that produced do; (services dead on arrival) and PID-1 dropping SIGTERM (30s stops, 0.07s with the trap).

the numbering has one visible scar: the frontend and backend tracks once claimed 0023 and 0024 simultaneously — the collision was kept in the index rather than rewritten, because the log is the history
