02the process

How I used agents and iterative design

1 · Researching open-source tools using agents + generating reports

  • nginx — reload-based config, wrong for per-second endpoint churn
  • Linkerd — effectively requires Kubernetes underneath
  • Envoy — drains, balancing, hitless config over an open protocol (xDS)
  • Cilium — load balancing and policy compile into eBPF programs inside the Linux kernel, and it's built as a Kubernetes CNI plugin. That replaces the exact layer this project exists to build by hand, and kernel-level packet steering is invisible where k-lite wants every mechanism watchable
  • Istio — same: needs Kubernetes under it
  • Traefik / Caddy — routing rules are dynamic, but the listening addresses are fixed at startup. k-lite needs a new VIP listener to appear at runtime every time a Service lands on a node, and both would still need our DNS server running beside them
  • Consul — discovery and policy in one tool, but it brings its own raft consensus and gossip cluster. That's a second distributed system bigger than k-lite itself, doing the job etcd already does

Agent chose: custom L4 proxy, with Envoy as the documented swap.

2 · Auditing agent decisions

a · custom L4 proxy → choosing Envoy

  • learning about the xDS gRPC protocols pushed toward it
  • easy-to-use open standard

b · choosing bbolt originally → using etcd

  • want a robust, battle-tested system that mirrors k8s

c · peer-to-peer internet communication over Wi-Fi to mimic the real thing → Tailscale as the mesh VPN

  • deferred the harder implementation until later
  • pushed the agent to actually research and complete a full working model (slide 11)

d · bad design for UI

  • more subjective, but good taste in the live UI
  • pull from real-world examples like turbopuffer + raft/paxos visualizations

3 · Design and research as much as possible up front

  • always better to have a good design up front, even if it requires lots of time
  • pull from real-world systems like Istio / Envoy / k8s
  • found /grill-with-docs to push the agent to question and iterate + document design choices

4 · Parallel subagents for speed + thoroughness

  • Claude Code CLI is great for this
  • manage workflows, cross-session communication (3 main sessions for infra + UI + HTML, with subagents for each)

03xDS in one breath

Envoy is configured by subscription, not by files

The proxy asks discovery services for its config and applies every update hitlessly.

LDSlistener discovery — which addresses and ports to bind, and the filter chain on each
RDSroute discovery — HTTP routing tables (unused here: every k-lite listener is plain L4 tcp_proxy)
CDScluster discovery — the named upstreams a listener can hand traffic to
EDSendpoint discovery — the addresses inside each cluster, with health attached
ADSthe aggregated stream — all of the above over one gRPC connection, ordered so a listener never references a cluster that doesn't exist yet

What crosses the ADS stream (Envoy ⇄ klited)

  • Envoy sends: its node.id once, then subscriptions per resource type
  • klited sends: a versioned snapshot per type — listeners (with RBAC), clusters, endpoints with health
  • Envoy answers every push with an ACK (applied) or a NACK (rejected, with the error) — klited logs NACKs
  • a new version pushes only when content actually changed; the swap is hitless
# abbreviated exchange envoy → DiscoveryRequest { node.id: "node-1", type: Cluster } klited → DiscoveryResponse { version: "1214", resources: [cluster b — EDS, round-robin] } klited → DiscoveryResponse { version: "1214", type: Endpoints, b: [10.44.128.6:80 HEALTHY · 203.0.113.7:20129 HEALTHY (mTLS)] } envoy → DiscoveryRequest { version: "1214", nonce: 42 } # ACK

06service discovery

Names resolve to a proxy, not an instance

own DNS + a VIP per (Service, Node)each node's instances hear their own node's answer — churn hides behind a fixed addresschosen

Who creates a VIP

  • Each (Service, Node) pair gets a VIP
    • a VIP is created by klited once a Node + Service exist and uses the first free address in 10.44.64.0/18
    • It stores it as a VIPAllocation (b.node-1 → 10.44.64.5)
  • a node's klite-net binds it on the infra pod's interface, and the node's Envoy opens the listener on VIP:port
  • kdns maps svc endpoints to service IPs
  • nothing else gets a VIP, instance containers use real bridge IPs colima assigns

07a node joins

From declared to Ready, on either home

    1. klite node add node-5 declares the Node and mints the token — K10<ca-hash>::node:<secret>. An agent for an undeclared name is refused.
    2. The agent dials out. It has no CA yet, so it verifies the certificate it's shown against the hash pinned inside the token.
    3. Register: the secret is checked in constant time, a CSR goes up, and a certificate comes back — CN=klite:node:node-5. The private key never left the machine.
    4. The same response carries NetBootstrap: infra IP 10.44.0.15, the VIP pool, ingress slice :20128–20159, the pinned infra image.
    5. The agent builds the infra pod — klite-net owns the netns and the published port slice, Envoy joins it — then opens its streams: WatchDesired down, ReportStatus up every 5s.
    6. klited stamps the node Ready and the scheduler starts counting it. 15 quiet seconds would mark it NotReady, 30 more evacuate its instances.

    klite-agent is the kubelet

    • holds the node's identity, builds the infra pod, drives Docker — create, stop, restart with backoff
    • owns readiness: reads klite-net's probe verdicts and turns them into instance phases
    • streams container logs up on request — klited can never dial a node
    • down (WatchDesired stream): the node's full desired snapshot on every change — its instances, plus the net config (DNS table, VIPs, probe targets, ingress listeners)
    • up (ReportStatus, every 5s + on change): every instance's phase, IP, and restart count — this is also the heartbeat

08identity

mTLS to communicate between nodes & the control plane

A token buys each node a certificate: the agent sends a CSR, klited's CA signs it, and the result lives on the machine's disk (~/.klite/agent/<node>/tls).

  • "valid" means the cert chains to the cluster CA, checked at every handshake
  • peer-to-peer ingress needs only the ca.crt file each Envoy already holds — any node cert the CA signed passes

09crossing machines

How traffic crosses machines: published ports behind mTLS

  • if EDS chooses an instance on another machine, the IP address looks like: internetNodesAdvertisedAddress:ingressPort
  • the remote machine chooses an IP it can receive open traffic on (its advertise address) and reports it to klited
    • klited picks a port from that node's slice per instance, and the node's Envoy holds the mapping of port → local instance docker IP
    • klited broadcasts advertiseAddress:port to every other node over EDS
  • EDS stores local instance IPs as their local version, so routing is all done on the node only
published ports behind node-cert mTLSthe join identity reused wholesale · ports live as stored allocations · listeners follow allocations, not health, so drains stay hitlesschosen

10reachability

Joining needs one reachable machine. Traffic needs all of them.

trafficdirectionwho must be reachable
controlagent → klited, always outwardonly klited's machine, on one port — a node behind hotel NAT joins and stays joined
dataEnvoy → Envoy, peer to peerevery machine hosting instances, on its advertise address + 32-port slice

NAT breaks exactly the second row, and quietly — joining only ever proved the first

caller ↓ / callee →reachable node
(routable IP)		NATed node
(or offline fallback)
reachable node✓✕ blackhole
NATed node✓✓ same machine

on one LAN this never bites: every node advertises the Mac's LAN IP by default, so traffic flows both ways out of the box (host.docker.internal is the offline fallback, KLITE_LAN=0 forces it). the blackhole is the open-internet case — a NATed node registers and looks healthy while traffic toward it dies

11the open internet

Internet clusters ride an overlay, not port maps

Control made the dial-out bet — one inbound address in the whole system. The data plane reintroduced inbound, and across the open internet "every node dialable" fails per network: a router rule per node, and carrier-grade NAT offers no inbound at all.

port forwarding + dynamic DNSa rule and a stable address per network, nothing behind CGNAT — kept as the raw path for all-static-IP setupsrejected as default
self-hosted headscaledrops the account, but the coordinator needs exactly the public endpoint whose absence motivates thisrejected as default
single-hub WireGuardno account, one udp/51820 forward total — spoke traffic hairpins through the hub, keys move by handrecorded variant
IPv6 end to endno NAT, no traversal — and no cluster has run it; an unexercised raw pathrecorded
native reverse tunnelsklited is already everyone's dial target — but that's a relay in the data path, the one thing the design refusesfuture
a Tailscale tailnetboth ends dial out, DERP relays carry what hole-punching can't, and k-lite changes zero lines — the tailnet IP is simply what nodes advertise and what klited serves. k3s ships the same integration shape, marked experimentalchosen
  • The tailnet sits in the coordination path, never the trust path — the cluster CA still signs everything, so cross-node traffic is our mTLS inside their WireGuard. Encrypted twice, deliberately: an overlay misconfiguration can't downgrade the cluster's own authentication.
  • Install order matters once: tailscale first, then restart klited — the serving cert walks interface addresses at boot, and skipping the restart is the documented x509-mismatch loop.
  • join.sh treats 100.64.0.0/10 three ways on purpose: detection refuses it, explicit values pass, and KLITE_VPN=tailscale derives one deliberately.
  • Disable key expiry for cluster machines — an expired tailnet node key (180-day default) looks exactly like a dead network.
  • Mixed clusters inherit a rule: every node advertises its tailnet IP, the Mac's local agents included. Tailscale keeps same-LAN peers on the direct local path, which is what makes the rule universal.

joining across the internet — printed by klite node add

curl -sfL https://…/join.sh | \ KLITE_URL=100.69.43.39:7443 \ KLITE_TOKEN='K10…' KLITE_NODE=laptop-1 \ KLITE_VPN=tailscale \ KLITE_TS_AUTHKEY='tskey-auth-…' KLITE_YES=1 sh - # installs tailscale (consented), joins the # tailnet, advertises tailscale ip -4, and # proceeds as any other join

12the live UI

The board is one more watcher

Browsers don't speak gRPC, so a small facade translates. Objects ride the same watch everything else uses, and calls ride a second feed built from Envoy's counters.

bootstrap: list, then watch — reconnect resets deletes carry the last body (PrevKV) traffic = counter deltas, polled 1s mock mode: an in-browser simulator, same client seam

13the CLI

Eleven commands drive everything

klite dials any replica over TLS with the admin token and fails over across a server list. Tables by default, -o json|yaml for machines.

commandwhat it does
klite apply -f …create or update from YAML — files, directories, stdin
klite get <kind> [--watch]list, narrow by name, or stream the same events the board rides
klite describe <kind> <name>full spec + status, including the scheduler's reason for a Pending instance
klite scale workload b --replicas 5set the count — scale-down drains victims, newest first
klite logs <instance> [-f]container output, tailed or followed — rides a stream the agent opened
klite delete …by file or kind+name — deleting a Node cordons, drains, then removes
klite drain <node> [--force]cordon + evacuation, progress streamed — the cordon survives on purpose
klite uncordon <node>reopen for scheduling — the explicit way back
klite policy check a cthe data plane's own evaluator answers, nonzero exit on denied
klite node tokenmint the CA-pinning join credential
klite node add <name>declare the Node and print the paste-ready join blocks
